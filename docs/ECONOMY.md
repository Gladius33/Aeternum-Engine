# Economy design — initial lazy production primitive

ProductionState is immutable and generic: stock and capacity in integer smallest units, amount per integer interval in seconds, last effective timestamp and fractional numerator carry. Use only 64-bit PHP. Max amount/capacity is 10^12 units and max interval 2,592,000 seconds. Saturation discards output and carry, with a threshold check before computing elapsed * amount to prevent overflow. Debit/credit never settle automatically: first advance to the effective event/command time. Debit rejects overspending, credit rejects overflow. Never store PHP floats or trust client-supplied balances.

This pure primitive is not yet a balance repository, ledger, market, resource definition registry or authorization system. The next integration must settle affected balances under the existing world transaction, persist state/ledger atomically, validate actor/world/asset scope, and test conservation and concurrent competing debits. Rate changes and capacity upgrades require settling prior production before changing the rule; define carry conversion explicitly.

## Reference economy (0007)
EconomyCommandHandler accepts a list of trusted ResourceDefinition objects. Commands economy.open, economy.settle and economy.transfer validate exact payload fields. Accounts are world-scoped (account ID, resource ID); initial grant comes from the definition, not the request. Reference state stores stock, timestamp and carry in a scalar map, bounded to 1,000 accounts. It is suitable for initial validation, not high-scale production. Transfers settle both participants at authoritative effective time, debit and credit the same resource, and reject insufficient stock, capacity overflow or self transfers. Positive production, initial grants and paired transfer entries are written to engine_resource_ledger in the same transaction. Replay verifies each line. No public caller can safely invoke economy.open or transfer until authenticated actor and ownership checks are implemented; all current inputs are trusted application commands. Timed resource-rate upgrades and their cost/production ledger effects are introduced in 0008.

## Timed upgrades (0008)
ResourceUpgrade definitions specify resource, resulting level, positive cost and duration, and improved rate amount. Configuration must be contiguous and increasing with fixed denominator and storage capacity. economy.upgrade settles to command time, charges configured cost, stores one pending ID per account/resource, and schedules completion in the same transaction. Completion uses the exact event due time, settles the prior rate and activates the new level without losing carry. Later projections apply the new rate only after that time. Cost and event production appear in the ledger; replay checks both. Trusted rule deployment must connect EconomyEventHandler to the same EconomyCommandHandler. Clients may not supply levels, costs, durations or rates. Authorization, cancellation, refunds, multi-resource costs and other domain actions remain open.

## Data-only packs (0009)
See schemas/game-pack-v1.schema.json and games/reference-*/manifest.json. GamePackLoader::load validates JSON bytes and computes their SHA-256; GamePack::rules creates trusted economy handlers without theme-specific PHP. Keep exact original bytes for pinned worlds, including whitespace. No arbitrary code, file path or URL execution. Schema describes field structure; PHP loader enforces resource constraints. Pack content identity does not authenticate authorship or prove the running PHP implementation matches an older release. Duplicate JSON object keys are not separately detected by PHP json_decode; use canonical producer tooling and reviewed artifacts. No untrusted pack upload endpoint.

## Player admission (0010)
Use executeForActor only after the application has authenticated the actor. Account ownership is relational and assigned by a trusted operator. Players may open, settle or upgrade their own assigned accounts, and transfer from their own account to an active assigned destination. The request ID is scoped to the actor. Public responses must use ActorReceipt or balanceForActor, not the internal full world snapshot. Authentication and user-facing interface are not implemented yet.
